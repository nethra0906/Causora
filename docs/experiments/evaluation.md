# Evaluation Harness

> **Build status — blueprint document.** Built: Hit@1 (plus a stricter "first instance" variant), Hit@3, MRR, edge recall, "cause reachable" and idempotency-bug diagnosis over **40 runs of four scenario types** and eight rule sets. Results in [results.md](results.md) are generated by `npm run eval`. Not built: S5–S7, the sampling experiment, weight tuning.

The harness is what makes Causora an evaluated system rather than a demo. It exists because
the fault injector **causes** the failure and therefore **knows the answer**.

> No metric values appear here. They are produced by real scenario runs in the implementation
> phase and written to `evaluation_results`.

---

## 1. Ground truth

Every scenario declares it, and the runner stores it before the workload starts:

```ts
groundTruth: {
  service:   'inventory-service',
  operation: 'inventory.reserve',
  faultType: 'handler_delay',
  expectedPatterns: ['DUPLICATE_WORK', 'IDEMPOTENCY_FAILURE'],
  expectedEdges: [
    { fromType: 'order.created',     toType: 'inventory.reserve', edgeType: 'TRIGGERED' },
    { fromType: 'inventory.reserve', toType: 'timeout.fired',     edgeType: 'TIMED_OUT_WAITING_FOR' },
    // ...
  ]
}
```

A candidate is **correct** when its `(service, operation)` equals the ground truth's and,
where the fault targets a specific attempt, its `attempt_number` matches.

### The integrity constraint

Ground truth must not reach the analysis pipeline. Three enforcement points:

1. The ranker's input type structurally omits `is_fault_injected` and `experiment_id`
   (`event-model.md` §3) — leakage is a compile error.
2. `FAULT_AFFECTED` edges are excluded from traversal unless `mode=ground_truth`, which the
   harness never sets when producing an investigation it will score.
3. A unit test asserts ranking is identical with and without the fault flags set.

Without all three, Hit@1 is meaningless. This is the single most important correctness
property of the evaluation, and it is the first thing a sceptical reader should check.

## 2. Metrics

| Metric | Definition | Measures |
|---|---|---|
| **Hit@1** | fraction of runs where rank 1 is correct | top-line usefulness |
| **Hit@3** | fraction where the correct candidate is in the top 3 | usefulness with a short list |
| **MRR** | mean of `1/rank` of the correct candidate (0 if absent) | ranking quality overall |
| **Graph completeness** | derived proven edges ÷ `expectedEdges` | reconstruction fidelity |
| **Contract compliance** | events with no `contract_violations` ÷ all events | instrumentation quality |
| **Pattern recall** | detected ÷ `expectedPatterns` | pattern library coverage |
| **Analysis latency** | investigation `duration_ms` | cost of the above |
| **Determinism** | identical candidate list across repeated runs on identical input | trustworthiness |

MRR is the primary metric for comparing rule sets; it is less brittle than Hit@1 across a
small number of runs, which matters when 30 runs is the realistic sample size.

## 3. Protocol

```
for each scenario in suite:
  for each ruleSetId in [default, ablation.*]:
    for repetition in 1..N:                     # N = 10 MVP, 30 for the final report
      reset databases
      load D1-baseline (so baselines exist)
      run scenario with ruleSetId
      wait for completeness verdict to leave PROVISIONAL (max 15s)
      for each failure produced:
        investigate
        score against ground truth
        write evaluation_results row
aggregate by (scenario, ruleSetId); report mean and standard deviation
```

Three details that are easy to get wrong and would invalidate the results:

1. **Baselines must be loaded first.** Without baselines, latency anomaly scores are zero and
   every candidate looks the same. The number produced would measure the bootstrap, not the ranker.
2. **Wait for quiescence.** Investigating a `PROVISIONAL` graph gives an unstable ranking, which
   shows up as variance and gets misread as ranker noise.
3. **Reset between runs.** Residual events from a previous run change baselines and can create
   cross-run duplicate edges.

## 4. The ablation study — the research contribution

**Question.** How much does root-cause accuracy depend on propagated causal metadata, versus
what can be recovered by inference?

**Method.** Identical raw telemetry (`D5`, replayed from `D2`'s stored envelopes) processed by
different rule sets. Only the rule set varies — the input bytes are byte-identical, which is
what makes this a controlled experiment.

| Rule set | Disabled rules | What it simulates |
|---|---|---|
| `default` | none | a fully compliant deployment |
| `ablation.no_causation` | `rule.triggered.causation_id` | async causality not propagated — **the most common real-world gap** |
| `ablation.no_retry` | `rule.retry.explicit` | retries not labelled |
| `ablation.no_idempotency` | `rule.duplicate.idempotency` | no idempotency keys, so duplicates undetectable |
| `ablation.no_timeout` | `rule.timeout.awaited` | timeouts not linked to what they awaited |
| `ablation.tracing_only` | all but `rule.parent.span` | what conventional distributed tracing alone provides |
| `ablation.inference_only` | all proven rules; inferred rules enabled | pure heuristic reconstruction |

**Hypotheses, stated in advance** so the result cannot be retrofitted to whatever happens:

- H1: `default` achieves high Hit@1 on the primary scenario — because the graph is almost
  entirely proven, this is close to a correctness check on the ranker, not a discovery.
- H2: `ablation.tracing_only` fails badly on the primary scenario, because the causal chain
  crosses two trace boundaries that span parentage alone cannot bridge. **This is the
  quantified version of Causora's central claim.**
- H3: `ablation.no_causation` degrades less than `tracing_only`, because
  topic/partition/offset inference recovers much of the producer→consumer link — and the cost
  shows up as a drop in candidate *labels* (STRONG → WEAK) more than in Hit@1.
- H4: `ablation.no_idempotency` barely changes Hit@1 but loses the `DUPLICATE_WORK` pattern and
  therefore the *explanation*, even when the ranking is still right.

**H4 is the most interesting hypothesis in the project**, because if it holds it means
ranking accuracy and explanatory quality are different things that degrade independently.
A tool can point at the right operation while being unable to say what went wrong — and the
distinction between "where" and "why" would be a genuine, defensible observation about
causality-aware tooling.

If a hypothesis is wrong, it gets reported as wrong. A disconfirmed hypothesis with real data
is a better result than a confirmed one with convenient data.

## 5. Threats to validity

Stated plainly, because an evaluation without this section invites exactly the criticism it
fails to anticipate.

| Threat | Severity | Response |
|---|---|---|
| **Both the app and the analyser are mine; I may have instrumented exactly what my rules need** | **High — the central criticism** | This is why the ablation exists: it measures performance when the convenient metadata is absent. It is also why the demo bug is a real check-then-act race rather than an invented failure. It remains a real limitation and must be stated, not argued away. |
| Scenarios are synthetic | High | No claim is made about production incidents. The claim is bounded to these scenarios, and the scenarios are published so others can judge them. |
| Scoring weights were tuned on these scenarios | Medium | Report results with the default weights **unchanged** from their initial declared values; if weights are tuned, report both before and after, and say which scenarios were used for tuning. |
| Small sample (30 runs, 3–7 scenarios) | Medium | Report standard deviation; make no significance claims. |
| Ground truth is the *injected* fault, not the *root cause* in a causal sense | Medium | Acknowledged: the injected fault is the intervention. The chain from fault to failure runs through a genuine bug, which is arguably the more interesting cause. Both are reported, and the distinction is discussed rather than elided. |
| Laptop timing variance | Low | Fixed container limits, repetitions, reported spread. |

The last threat is worth expanding, because it is a point in the project's favour rather than
against it. In S1, the *injected fault* is the delay, but the *defect* is the non-transactional
idempotency guard. Causora ranks the delayed operation first — which is the right answer for
"where did this chain start" and the wrong answer for "what should I fix". Scenario S7
(`inventory_fix`) demonstrates that distinction: same fault, fixed guard, no failure. Naming
this limitation precisely is more valuable than pretending the tool identifies defects.
